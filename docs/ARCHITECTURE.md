# Architecture

Use a modular monolith with a Rust Axum API, PostgreSQL as the system of record and storage for the initial bounded text-file class, and a Next.js web client. Separate object storage is deferred for larger/binary files. Provider adapters run inside the application boundary. The stdio MCP binary is a thin transport adapter: product tools call the authorized API, never tables independently. Independent service scaling is deferred until justified.

Every request that touches workspace data must resolve an authenticated principal and authorized workspace before reading or writing. Database rows carry `workspace_id`; storage keys are generated by the service and never derived directly from user supplied paths.

## Planned shared project state

The source of truth consists of immutable file versions, captured messages, action outcomes, memory revisions and user approvals. A derived project summary can be rebuilt from those sources. Retrieval is a view over authorized data, not a separate authority.

Planned flow: authenticate actor -> authorize workspace and operation -> select context and source versions -> call provider -> store visible response -> propose changes -> approve when required -> apply conditional write -> publish activity -> refresh derived context. Keep long provider requests outside database transactions.

Add boundaries incrementally: identity/authorization, files/versioning, conversations, activity, memory, retrieval, provider adapters and Passport. The HTTP API and MCP transports must call the same authorized services. Avoid unused placeholder crates.

## Data model changes required before implementation

- Add agent connections and grants with workspace, principal, operations, permitted resource scope and revocation state.
- Separate folders from files; keep object keys generated by the server and validate workspace consistency through composite references.
- Add file versions with content hash, object reference, actor and parent version. Restore creates a new version; compare-and-swap protects writes.
- Add conversations/messages with origin, external IDs when present, capture coverage and privacy scope. Deduplicate imports without merging unrelated conversations.
- Add action events with actor, task, input references, attempted/completed/failed status, safe result summaries, request IDs and affected versions.
- Add memory candidates/revisions, approval state and source links to exact messages or file versions. Store derived-summary lineage and invalidate downstream summaries as well as individual memories.
- Add task state and context packet manifests: included source IDs/versions, retrieval cutoff, permission scope, token budget and omissions.
- Add versioned Passport snapshots and import validation. Imported text is untrusted evidence; it cannot grant permissions or auto-approve decisions.

The current SQL migration covers users, workspaces, memberships, files, memories and evidence with a tested restricted role (docs/DATABASE.md). It does not yet implement the entities above. Database tests must exercise a restricted application role, not a superuser. Policies must distinguish read/write roles and prevent membership self-escalation; transaction context values alone are not authentication.

## Capture and retrieval

In-app provider adapters persist user-visible input and output through AIDrive. External clients can only contribute content exposed by their permitted integration, explicit handoff tools or user import. Never infer that MCP grants access to all client conversations.

Index only captured authorized sources. Apply access restrictions before retrieval and again before delivery. Private source material must not leak through shared summaries, embeddings, caches or Passport exports. Store enough lineage to enforce deletion and permission changes across derived data. Do not log secrets or full prompt bodies in ordinary diagnostic logs.

Use source/version invalidation before attempting semantic conflict detection. Candidate extraction is asynchronous and idempotent; failed extraction leaves the source intact and visibly pending. Keep retrieval bounded and allow source inspection when the selected context is insufficient.

## Writes and failures

Use explicit task and idempotency identifiers for retryable mutations. Persist file bytes and version metadata with a recoverable staging/commit sequence; interrupted writes must not create an apparently available file without content. Validate size and MIME/text handling before extraction. Treat filenames, imported text and tool results as untrusted input.

Provider adapters require bounded timeouts, cancellation, recorded usage and explicit incomplete/failed response states. A tool proposal, attempted call and confirmed durable change are separate events. Start with human-approved sequential edits. Multi-agent scheduling and merging are later work.

## Current status

Implemented locally: API readiness, sessions, workspace isolation, revocable agent grants, versioned text files, web upload/edit/history/restore and MCP file tools (see the dated ROADMAP evidence). Conversations, approved handoffs, shared memory and provider adapters remain planned. Compose and remote CI remain unobserved; a successful health response is not a release gate.

## Implementation decisions for G0-G6

These are planned constraints, not implemented capabilities. For the pilot, workspace equals project isolation boundary. Identity comes from server-validated authentication; transaction-local user/workspace settings express that identity to RLS. Agent context additionally carries a principal and grant scope. Human membership alone is insufficient to authorize a restricted agent.

G0 update 2026-11-18: SQLx 0.8.6 is pinned in the dedicated `aidrive-db` migration utility; it was built with WSL Rust 1.98.0 and dependency resolution honored the declared Rust 1.88 baseline (that compiler itself is not yet tested). Migrations use owner credentials in a separate lifecycle from runtime access. Additive migrations, a verified legacy-schema baseline and an isolated PostgreSQL test instance are implemented; see DATABASE.md. The API has not yet adopted SQLx for runtime queries.

Make file versions and approval revisions immutable under ordinary application operations. Store mutable head/status references separately. Authorization and mutation preconditions are checked in the same transaction as the database mutation and action record. Restrict the ability to rewrite creator fields; the modifying actor belongs to a new version/event. A transactional outbox or equivalent durable job record schedules extraction/index updates; job handlers are idempotent.

Source invalidation has a synchronous eligibility barrier: a changed source commits an incremented revision/invalidation record before the next retrieval can treat dependent knowledge as current. Derived jobs may lag but retrieval must reject stale dependencies, including transitive summary dependencies. Approval uses compare-and-swap against the proposed memory revision and source versions.

Context dispatch and revocation need an explicit ordering. Serialize the final grant check and dispatch claim against revocation; a revoke committed before that claim blocks delivery. Calls already admitted are recorded as in-flight and cancelled where possible; they may have exposed context and cannot be recalled. Every resulting tool mutation rechecks current authorization. Do not keep a database transaction open while waiting for model generation. Record precisely when a manifest was assembled, admitted and sent; surface ambiguous delivery states.

Retrieval starts with workspace/grant filters, exact identifiers, time/version/status filters and PostgreSQL text search. Evaluate language configuration for Armenian and English. Add embeddings/reranking only if development-set evidence improves recall/answer quality enough to justify latency, cost and additional deletion lineage. Never let approximate similarity authorize access. Preserve eligible source references even when the token budget omits their text; show omissions and permit scoped follow-up retrieval.

Deletion commits a denial/tombstone immediately and queues physical cleanup. Recompute or invalidate derived summaries with deleted ancestors. Audit records retain only permissible minimal metadata rather than embedding deleted private content. Backup restoration must reconcile deletion records before serving; define how tombstones survive restoration to an older snapshot. Retention policy and externally delivered copies are part of the user-visible contract.

## Durable text files — implemented 2026-11-19

For UTF-8 `.txt`/`.md` files up to 262144 bytes, migration 0006 stores content, SHA-256, parent/source version, actor, head and completed action record in one PostgreSQL transaction. Restore creates a new version. Editor/owner writes require a matching base version; overlapping writes from one base yield one winner and one conflict. Request UUIDs deduplicate exact retries, including after later versions exist; changed input under the same request ID is rejected. Old retries return the original result and the observed current head, and never rewind the head. Migration 0007 additionally records the agent ID alongside the accountable issuing user.

Research checked 2026-11-19: [PostgreSQL TOAST](https://www.postgresql.org/docs/17/storage-toast.html) supports out-of-line storage of large variable-length values; [transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html) informs row-lock and conditional-write ordering. We chose bounded database text over a separate local object store to avoid publishing metadata without its bytes and simplify backup/restart consistency. Tradeoff: every version consumes database/WAL/backup space; quotas and binary/object-storage lifecycle remain future work. The former staging requirement applies when a separate byte store is introduced; this implementation has no independent byte-staging phase.

[OWASP upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) informed extension, name, permission and size checks. The server rejects unsupported names, path separators, control characters, NUL and oversized UTF-8 content. Uploaded content is shown as escaped text, never rendered as HTML/Markdown; downloads force text/plain, attachment and nosniff. Browser file decoding rejects malformed UTF-8. File metadata and history have bounded cursor pages; content is read one version at a time. Legacy unversioned metadata is preserved and excluded from these file routes rather than pretending its bytes were imported.

The web editor keeps a rejected draft, offers a side-by-side comparison and requires explicit selection of a new base before overwriting a newer version. Ambiguous saves retain the exact request for retry. Draft guards cover reload, file/space switching and sign-out; drafts and pending requests are held in memory, not durable offline storage. There is no automatic merge or line-level diff yet.

## Agent metadata access — initial slice 2026-11-18, extended by migration 0007

The initial agent principal was a workspace-bound credential with `workspace:read` (workspace ID/name only). Migration 0007 adds `files:read` and `files:write`, with bearer-only API routes and MCP tools. Owner management remains session-authenticated. Agent file requests validate the current grant and then install transaction-local issuer/workspace/agent context; write checks enforce scope and record both accountable owner and agent. The web key form still issues metadata-only keys; broader scopes currently require the API. Memory and provider calls are not enabled by these credentials.

Each credential contains 256 random bits; only its SHA-256 digest is stored in a private table. Secrets are returned once with `Cache-Control: no-store`, expire after seven days, and cannot be recovered through listing. A client request UUID prevents duplicate issuance on retries: a used UUID returns 409, so an acknowledged-lost secret must be revoked and replaced. This deliberately trades convenient retry recovery for no reversible secret storage. The web UI retains the request UUID across ambiguous failures and explains how to revoke an unrecoverable key.

PostgreSQL definer functions with pinned search paths enforce current owner membership and selected workspace for management. Reads lock the issuer membership and then the grant row, recheck expiry after a possible lock wait, and return only metadata. Revocation and owner-departure triggers take conflicting locks; demotion/removal permanently revokes the issuer's keys, including after rejoining or promotion. A read admitted before revocation may already have returned data; this is not a guarantee of recalling a response or cancelling future provider work. No database transaction spans model generation.

Research checked 2026-11-18: [OWASP authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) supports least privilege, default denial and per-request authorization; [PostgreSQL 17 explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html) supplies conflicting row locks for ordering reads and revocation. Opaque database-checked credentials were chosen over self-contained JWT permissions so revocation and membership changes are effective on the next check. Tradeoff: every authorized read needs the database, and a lock wait can delay or fail a request. Hosted rate limits, bounded list pagination and an activity/audit stream remain required future work.

## Research and tradeoffs — checked 2026-11-17

| Primary source | Decision / implication | Tradeoff |
| --- | --- | --- |
| [PostgreSQL roles](https://www.postgresql.org/docs/17/database-roles.html) and [row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) | Separate cluster-level test credentials; retain restricted runtime role and service authorization | More environment setup; RLS alone cannot authenticate a request or protect every provenance field |
| [SQLx Migrator](https://docs.rs/sqlx/latest/sqlx/migrate/struct.Migrator.html) | Use migration tracking/validation and keep locking enabled; verify selected version compatibility | Adds a dependency and an explicit migration lifecycle; existing untracked schema needs a verified baseline |
| [PostgreSQL text search](https://www.postgresql.org/docs/17/textsearch-intro.html) | Establish an inspectable lexical retrieval baseline before optional hybrid search | Semantic/paraphrase and multilingual recall may require improvement; decide from measured failures |
| [LongMemEval](https://arxiv.org/abs/2410.10813) | Evaluate updates, time, multi-session evidence and abstention, separately from retrieval | Public benchmark dimensions do not test all our permissions, provenance or file operations |
| [MCP authorization, revision 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) | Separate local stdio credentials from HTTP authorization; pin/test actual client and SDK compatibility | One supported client initially; protocol support does not supply external transcript capture |
| [OWASP prompt-injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) | Treat retrieved/imported content as untrusted, constrain tools, validate outputs and require authorized execution | Instruction labeling alone is insufficient; application boundaries must enforce permissions |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | Target AA behavior, verify keyboard/focus/errors and perform manual assistive-technology checks | Automated accessibility tools cover only part of the required behavior |

These sources support the method choices; PRODUCT.md's numeric targets and ROADMAP.md's estimates are our proposed acceptance policy, not source-derived benchmarks or guarantees.
